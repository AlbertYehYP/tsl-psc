# TSL 船隊事故追蹤系統

德翔海技 TSL MARTEC 的事故登錄與 PSC（港口國管制）檢查系統。

網站分成兩個主分頁：

- **事故管理（主軸）**：船管公司事故登錄器。所有事故都在這裡編號、追期限、歸檔、結案；PSC 檢查有缺失時自動成為 O 類事故。
- **PSC 檢查**：每一次 PSC 檢查（含 NIL 無缺失）的完整資料與統計。有缺失的檢查同時是一件事故，兩邊用事故編號與檢查編號互相連結。

- **前端**：GitHub Pages（本 repo，純靜態網頁）
- **資料庫**：Google 試算表 `TSL_PSC_DB`（放在指定的 Google 帳號）
- **檔案歸檔**：Google Drive 資料夾 `TSL PSC System`
- **後端**：綁定在試算表上的 Google Apps Script，負責登入驗證、事故編號配號、寫入資料、存檔

> **repo 不放任何資料。** PSC 紀錄、事故登錄、上傳的報告都只存在 Google 試算表與 Drive。GitHub Pages 的網址即使公開，沒有登入也看不到資料。

## 功能

| 主分頁 | 子分頁 | 內容 | 權限 |
|---|---|---|---|
| 事故管理 | 事故分析 | 事故件數、進行中、RCA 逾期、Tier、PSC 有缺失未立案、每月事故（PSC / 其他）、待處理清單、事故性質、責任單位、船舶與管理公司排名 | 全部 |
| 事故管理 | 事故登錄與處理 | 事故登錄器；點開每件事故可看期限、上傳文件（船方報告、Template 1–5C）、編輯簡述與矯正措施、結案。PSC 事故直接開啟對應的檢查與缺失矯正 | 檢視：全部；登錄：editor 以上 |
| PSC 檢查 | 總覽 | 每月檢查、MOU 區域、缺失類別、高頻代碼、港口國、船舶排名、重複缺失 | 全部 |
| PSC 檢查 | 檢查登錄 | 新增／編輯 PSC 檢查（含 NIL）、自動配發事故編號、上傳 PSC 報告與矯正報告 | 檢視：全部；登錄：editor 以上 |
| PSC 檢查 | 缺失查詢 | 所有缺失逐項查詢，可複製成 CSV | 全部 |
| PSC 檢查 | 船舶檔案 | 依 IMO 彙整每艘船的檢查歷史（含改名前紀錄）與 NK 資料 | 全部 |
| PSC 檢查 | PSC 窗口 | Tokyo MOU 檢查窗口與 Priority I / II、官方與估算 SRP、NK 到期提醒 | 全部 |
| PSC 檢查 | 索賄分析 | 依 MOU 區域、港口國、港口、年度的發生率、金額範圍、談判價碼 | 依 `bribe_roles`（預設 admin、editor） |
| PSC 檢查 | 代碼參考 | 缺失類別、處理代碼、已開立過的代碼 | 全部 |
| 系統管理 | — | 使用者、編號設定、MOU 對照表、資料檢核、NK 匯入、船隊資料 | admin |

### 為什麼拆成兩個主分頁

- 每個分頁只對應一組資料表：事故管理 = `Incidents`（+ 非 PSC 事故的 `Documents`）；PSC 檢查 = `Inspections`、`Deficiencies`。組員要改哪一類資料，就去哪個分頁或試算表分頁。
- 有缺失的 PSC 檢查只存一份資料（在 `Inspections`），`Incidents` 只放事故編號、等級與狀態，用 `insp_id` 連回去，不會重複維護。
- 事故的統計（件數、逾期、Tier）和 PSC 的統計（檢查次數、NIL 率、MOU 區域）分開算，分母不會混在一起。

## 編號規則（與事故追蹤編號系統 v2.0 結合）

詳細說明見 [docs/NUMBERING.md](docs/NUMBERING.md)。

- **事故編號**：`[公司碼]-[船名]-[YYYYMMDD]-[等級][類型]-[序號]`，例如 `FLEET-TS KOBE-20260911-3O-01`
  - PSC 案件類型一律為 `O`。
  - 等級：留置為 Tier 2；未留置時，缺失達 6 項或開出 ISM 缺失（15xxx）也是 Tier 2；其餘是 Tier 3。門檻可在「系統管理」調整。
  - 序號：同一艘船同一天的第幾件事故，PSC 和非 PSC 一起計算，不會跟事故登錄器撞號。
- **NIL（無缺失）檢查**：不立事故編號，只有檢查編號 `PSC-[YYYYMMDD]-[IMO]`。
- **缺失編號**：`[事故編號]-D01`、`-D02`…
- **文件命名**：`[事故編號]_[文件代碼]_[序號].[副檔名]`，例如 `FLEET-TS KOBE-20260911-3O-01_RECT_01.pdf`
- **歸檔路徑**：`TSL PSC System/PSC/[年]/[事故編號]/`；NIL 檢查放在 `PSC/[年]/NIL/[檢查編號]/`；非 PSC 事故放在 `事故/[年]/[事故編號]/`
- **期限**：Tier 1、2 為 2 小時 / 24 小時 / 14 天，Tier 3 為 12 小時 / 48 小時 / 21 天。新事故會把期限寫入 Incidents；匯入的舊事故依事故日期與等級推算 RCA 期限。
- **非 PSC 事故結案**：需要先歸檔 RCA（Template 4）或結案確認（Template 5C）；可以選「仍要結案」略過。

## 部署步驟（約 30 分鐘，只需要做一次）

以下全部用**指定的 Google 帳號**操作。

### 1. 建立資料庫試算表

1. 到 Google Drive 上傳 `TSL_PSC_DB.xlsx`（另外提供，不在 repo 內）。
2. 右鍵 →「選擇開啟工具」→ Google 試算表，再用「檔案 → 另存為 Google 試算表」存成原生試算表，命名為 `TSL_PSC_DB`。
3. 確認有以下分頁：Inspections、Deficiencies、Documents、Incidents、Vessels、Companies、RiskProfiles、MOUMap、Rules、Ports、NKStatus、Users、Settings、AuditLog。

### 2. 安裝 Apps Script 後端

1. 在試算表選「擴充功能 → Apps Script」。
2. 「專案設定」勾選「在編輯器中顯示 appsscript.json 資訊清單檔案」。
3. 建立三個檔案，內容分別貼上本 repo 的：
   - `apps-script/Code.gs`
   - `apps-script/core.gs`（與 `assets/core.js` 內容相同）
   - `apps-script/appsscript.json`
4. 在編輯器選函式 `setup` → 執行，依畫面授權。它會補齊分頁欄位、把您設為 admin，並在 Drive 建立 `TSL PSC System` 資料夾。
   - 授權範圍包含寄信（每日提醒）與排程觸發（每日 07:00）。
5. 重新整理試算表，上方會出現「TSL PSC」選單。執行「套用欄位下拉選單與保護」。

### 3. 建立 Google 登入用的 Client ID

1. 到 [Google Cloud Console](https://console.cloud.google.com/) 建立專案（名稱例如 `tsl-psc`）。
2. 「API 和服務 → OAuth 同意畫面」：
   - 公司是 Google Workspace：使用者類型選「內部」。
   - 個人 Gmail 帳號：選「外部」，把要使用系統的人加入「測試使用者」（最多 100 人）。
   - 範圍只需要 `openid`、`email`、`profile`。
3. 「憑證 → 建立憑證 → OAuth 用戶端 ID」，類型選「網頁應用程式」：
   - 「已授權的 JavaScript 來源」加入 `https://<您的 GitHub 帳號>.github.io`（測試用可再加 `http://localhost:8000`）。
4. 複製產生的 Client ID，貼到試算表 **Settings** 分頁的 `google_client_id`。

### 4. 部署 Apps Script 網頁應用程式

1. Apps Script 編輯器右上「部署 → 新增部署作業 → 類型：網頁應用程式」。
2. 執行身分：**我**；誰可以存取：**所有人**。
   - 這裡的「所有人」只代表網址可以呼叫；每個請求都必須帶有效的 Google 登入憑證，而且帳號要在 Users 分頁中才會被接受。
3. 複製網頁應用程式網址（結尾是 `/exec`）。

### 5. 發布前端到 GitHub Pages

1. 建立 GitHub repo，把本資料夾全部內容推上去。
2. 編輯 `config.js`，填入：
   - `apiUrl`：第 4 步的 `/exec` 網址
   - `googleClientId`：第 3 步的 Client ID
   - 這兩個值不是密碼，可以提交。
3. repo「Settings → Pages」，Source 選 `main` 分支、根目錄 `/`。
4. 等 1–2 分鐘，打開 `https://<帳號>.github.io/<repo>/`。

> GitHub Pages 用在 private repo 需要付費方案（Pro / Team / Enterprise），而且網頁本身一樣是公開網址。資料安全靠 Google 登入與 Users 名單把關，不靠 repo 是否私有。

### 6. 開通使用者與分享資料夾

1. 用 admin 登入網站 →「系統管理」→ 新增使用者，填 Google 帳號 Email 與角色：
   - `viewer`：只能查閱
   - `editor`：可以登錄案件、上傳文件、結案
   - `admin`：另外可以管理使用者、船隊資料與設定
2. 到 Drive 把 `TSL PSC System` 資料夾以「檢視者」分享給同一批人，文件連結才打得開。
   - 上傳是由 Apps Script 以部署者身分寫入，使用者本身不需要 Drive 編輯權限。

## 組員共同編輯 Google 試算表

試算表可以直接分享給組員「編輯」。網站與 Apps Script 每次都即時讀取試算表，所以在試算表改的內容會馬上反映在網站上。

**可以直接改的**
- 各分頁的一般欄位：港口、缺失內容、處理代碼、矯正措施、改正日期、Bribe 欄位等。
- 日期可以打 `2026/10/2` 或 `2026-10-02`，缺失代碼可以打 `7109`；系統讀取時會自動統一成 `2026-10-02`、`07109`。
- 船舶改名、換管理公司：在 Vessels 分頁把舊資料填失效日，再新增一筆同 IMO、填生效日的資料。

**請不要動的**
- 第一列欄位名稱（系統依欄名讀寫）。
- 系統編號欄：`insp_id`、`tracking_no`、`def_id`、`doc_id`、`file_id`、`url`。
- 新案件請用網站登錄，才會自動配號並同步事故登錄器。

**保護與檢核**
- 第一次部署後，在試算表選單「TSL PSC → 套用欄位下拉選單與保護」。
  - 狀態、等級、Y/N 等欄位會變成下拉選單。
  - 標題列與系統編號欄改動時會跳出警告（不會鎖死）。
- 改完後執行「TSL PSC → 檢核資料」，問題會列在 `DataCheck` 分頁。
  - 網站的「系統管理 → 資料檢核」結果相同。
  - 檢核項目：編號重複、缺失找不到對應檢查、NIL 卻有缺失、代碼不是 5 碼、IMO 不在船隊資料、同船生效期間重疊等。
- 每一次修改都可以在試算表的「檔案 → 版本記錄」查到是誰改的；網站上的操作另外記在 AuditLog 分頁。

## 索賄（Bribe）紀錄

- 每次 PSC 檢查可以記：對方要求金額、實付金額（USD）、香菸數量、其他實物、說明。
- 狀態自動判定：`Y` 有付出、`R` 有索取但未付、`N` 無。
- 歷史資料已從原始紀錄解析，例如 `$ 1200 + 4 cigarettes`、`40 Cig+Paint`。
- 只有 Settings 的 `bribe_roles` 列出的角色看得到；其他角色從 API 就拿不到這些欄位。
  - 但試算表本身的編輯者都看得到，分享試算表時請留意。

## 事故規範（3-TSTB-VSL-P002 第 2 版）

- 規範存在試算表 **Rules** 分頁（網站：事故管理 → 事故規範），不寫死在程式裡：
  - `tier`：通報分級與時限（立即通報／初步報告 小時、進度更新間隔 日、RCA 日）。
  - `major`：4.1 重大事件分級（主持人、最低通報分級、海損／死亡／延誤／受傷的數值門檻，數字包含本數）。
  - `type`：事故性質代碼 M／N／C／P／E／S／F／T／O。
  - `param`：準時率目標（95%）、重大事件進度更新間隔（7 日）、保存年限（5 年）、結案前須歸檔的文件。
- **分版本**：每列有 `rule_set` 與 `valid_from`。每件事故依「事故日期當時有效」的版本計算，改版不會影響舊帳。程序書正式發行或改版時，在網站按「新增規範版本」，再逐條修改。
- 系統依規範自動檢核並提醒：
  - 4.2.4.2 通報分級低於重大事件對應級別；
  - 4.1 重大事件未成立應變小組；
  - 依數值可能達 4.1 等級；
  - 各階段報告逾期；
  - 重大事件進度更新超過間隔；
  - 已結案但 6.6.4 四項未確認。
- **通報時限準時率**（6.5.5、評比表 ≥95%）：實際提交日以事故頁填寫的日期為準，沒填時以最早歸檔的 FLASH／INIT／RCA 文件日期計。不可抗力不計入；匯入的舊事故沒有任何填報紀錄時標為「未填報」，也不計入。

## 在網站修改事故（舊帳修正）

- 事故頁「編輯事故」可以修改所有欄位：日期、船舶、公司碼、分級、性質、單位、PIC、地點、簡述、4.1 重大事件資料、應變小組、各階段期限與實際提交日、不可抗力、狀態與結案確認、矯正措施。
- 事故編號預設不變。管理員可勾選「重新編號」：舊號保留在 `former_no`，相關檢查、缺失、文件的 `tracking_no` 同步更新（Drive 上的檔名不會改）。
- 期限可以直接改（例如合約期限較短），原因寫在「期限調整原因」；也可以勾「依規範重算期限」。
- 管理員可以把非 PSC 事故標為「作廢」，作廢的事故不列入統計。
- 每次修改都記在 AuditLog。

## 地圖（PSC 檢查 → 地圖）

- 2D 平面（可縮放、平移、框選範圍）與 3D 地球（拖曳旋轉、滾輪縮放）。
- 指標：缺失項數、檢查次數、平均缺失、留置；有權限的角色另有索賄次數、發生率、實付金額。
- 呈現：長條或熱力。國家底色依國家合計。
- 點港口、點國家、選 MOU 區域或框選，地圖會拉近，右側列出該範圍的港口排名，以及缺失類別或各年度索賄。
- 港口座標存在 **Ports** 分頁（系統管理 → 港口座標）。新港口沒有座標時，暫用國家中心點。
- 地圖使用 d3（cdn.jsdelivr.net）與 `assets/world-110m.json`（Natural Earth 1:110m，公有領域）。

## 配色與動態

- 頁首右上可選配色：自動（依系統淺色／深色）、海霧、沙岸、森林、晴空、夜航（深色）。選擇記在各自的瀏覽器。
- 頁面切換、彈出視窗、提示訊息一律「淡入時由下往上、淡出時繼續往上」；系統設定「減少動態效果」時不播放。

## MOU 區域（檢查體系）

- 每次 PSC 檢查的 `mou` 欄記錄該港口國歸屬的體系，例如 Tokyo MOU、Indian Ocean MOU、Abuja MOU、Riyadh MOU、Paris MOU、Viña del Mar；美國記為 `USCG`，台灣記為 `Taiwan MPB`（兩者都不屬於任何 MOU）。
- 對照表在 `MOUMap` 分頁（網站：系統管理 → MOU 對照表），組員可以直接增修：
  - `port` 空白代表全國；有填港口的列優先。例如加拿大預設 Tokyo MOU，Halifax、Montreal 屬 Paris MOU。
  - `also` 記錄同時加入的其他 MOU（例如澳洲也是 Indian Ocean MOU 成員），只做說明。
- 新登錄的檢查依港口國自動帶入 MOU，表單上也可以改。
- 改了對照表後，按「補標空白的檢查」或「全部依對照表重新套用」。
- 資料檢核會提醒：MOU 空白、MOU 與對照表不一致、對照表缺國家。
- 原總表的「MOU」欄只是 Tokyo MOU 區域的 V 記號，其中 6 筆有誤（Lome 3 筆、Mundra 1 筆誤標 V；Manzanillo、Sydney 各 1 筆漏標），已改用國家對照。

## Tokyo MOU 檢查窗口與風險提醒

- **窗口**：依資料庫內最近一次 MOU 區域為 Tokyo MOU 的檢查日加上 SRP 等級推算，每天自動重算。
  - HRS 2–4 個月、SRS 5–8 個月、LRS 9–18 個月。
  - 超過窗口是 Priority I，在窗口內是 Priority II。
  - 其他 MOU 的檢查（例如 Lome、Abidjan、Dar es Salaam、美國、中東）不會重算窗口。
- **估算 SRP**：系統依 NIR 參數另外估算，與官方不同時會標記，用來發現資料錯誤。

### 官方 SRP 與公司績效的自動更新（排程）

Tokyo MOU 沒有公開 API。APCIS 需要帳號登入，公開資料庫也註明未經 Tokyo MOU 許可不得轉載或用於其他網站，所以系統**不做自動爬取網站**。可以排程的是「收件匣」：

1. 在 Settings 填 `alert_emails`。
2. 在試算表選單執行「TSL PSC → 安裝每日 07:00 排程（匯入 + 窗口 + 提醒）」。系統會在 Drive 建立 `TSL PSC System/Tokyo MOU 收件匣`。
3. 拿到新的 PSC Inspection Window 檔（格式同 `TSL_PSC_analysisWindow.csv`）時，存成 **CSV UTF-8** 丟進收件匣。
4. 每天 07:00 排程會依序：
   - 匯入收件匣內的 CSV（官方 SRP、公司績效），成功的檔案改名加日期後移到 `已匯入`；
   - 重算所有船的窗口，更新 `PSCWindow` 分頁；
   - 寄出提醒信：匯入結果（成功／失敗原因）、Priority I / II、即將進入窗口、NK 到期、RCA 期限已過仍未結案的事故。
- 不想等排程：試算表選單「立即匯入收件匣的 Tokyo MOU 窗口檔」，或在網站「PSC 窗口」頁直接上傳 CSV。
- 收件匣只接受 CSV；Excel 檔請先另存為 CSV。
- 如果之後取得 Tokyo MOU 書面同意，才考慮改成直接抓取官方資料。

## 與船舶履歷監控系統（NK 資料）共用

- 兩個系統以 **IMO** 串接。
- 在「系統管理 → 匯入船舶主檔 / NK 資料」選擇船隊監控系統 repo（tsl-fleet-monitor，未加密版）的 `fleet-data.js`，整個船隊一次匯入；也可以貼上單艘或多艘的 SHIP JSON（survey-status-schema v2）。系統會：
  - 依 IMO 對應船隊資料（同一 IMO 的改名 / 換管理公司前後各列都會處理）；
  - 寫入方式「船級欄位以 Class 資料為準」（預設）：船級、船級號、船旗、船籍港、登記船東、ISM 公司、建造日期、GT / DWT、TEU 與系統不同時，直接改成 Class 的值（例如裝脫硫塔後 TEU 略減）；其他欄位（如造船廠中文簡稱）只補空白。哪些欄位以 Class 為準，可在試算表 Settings 分頁的 `nk_class_fields` 調整；
  - 改名 / 換管理公司前的舊列（有失效日）保留當時的船旗、船東等資料，只更新建造日期、GT、DWT、TEU 這類船舶本身不變的欄位；
  - 匯入後跳出清單，列出補了哪些空白、改了哪些值、哪些差異沒改。另有「只補空白欄位」和「全部以主檔覆蓋」兩種方式可選；
  - 把證書效期、檢驗窗口、Conditions of Class 存進 `NKStatus` 分頁（每艘船整批換新；系統裡的資料若比主檔新則保留）；
  - 在「PSC 窗口」頁與船舶檔案顯示到期提醒。
- 船隊監控系統更新 `fleet-data.js` 後，再匯入一次即可同步，重複匯入不會產生重複資料。
- 加密版（tsl-fleet-monitor-secure）的資料無法讀取，請用未加密版的 `fleet-data.js`。
- 欄位對照見 `TSL_船舶資料共用性與PSC窗口檢核.xlsx`。

## Tokyo MOU 績效色標（船舶檔案）

- 「PSC 檢查 → 船舶檔案」每艘船的卡片依 Tokyo MOU 公司績效算法上色（NIR information sheet §3）：
  - 缺失比 = (ISM 缺失 × 5 + 其他缺失) ÷ 檢查次數；留置率 = 留置次數 ÷ 檢查次數；
  - 與 Tokyo MOU 平均缺失指數（2026-07-01 ~ 2027-06-30：2.64）、平均留置指數（3.84%）比較，相差超過 1（留置率 1 個百分點）為高於 / 低於平均；
  - 依績效矩陣分 Very Low（紅，高風險）、Low（橘，偏高風險）、Medium（黃，一般）、High（綠，低風險）。
- 期間可選「依目前篩選」（年度、MOU、管理公司等篩選都會影響）或「近 36 個月 Tokyo MOU」（與官方公司績效算法相同）；排序可選缺失件數、風險、缺失比。
- 上方「管理公司績效」表列出 5 家 DOC 公司（FML、V.Ships、BSM、T.S. Lines、Teh Shipping）的系統試算績效、Tokyo MOU 官方績效（PSC 窗口匯入）與是否在 Tokyo MOU 高績效公司名單。
- 平均指數、船旗與 RO 績效名單、高績效公司名單放在試算表 Settings 分頁，也可在「系統管理 → Tokyo MOU 年度指數與名單」修改；每年 7 月更新一次（高績效公司名單每季）。船旗與 RO 名單也用於「PSC 窗口」的估算 SRP。


## 台灣港口國檢查（v1.16）

台灣不是任何 MOU 的成員，港口國檢查由交通部航港局（MPB）執行。系統把台灣的檢查記為 MOU「Taiwan MPB」（畫面顯示「台灣 航港局」）：

- **RightShip**：報告頁「登錄 RightShip」輸入平台查得的 Safety Score（1–5，可標 indicative）、DOC Subscore、GHG Rating（A–E）與日期，存在新分頁 `RightShip`（保留歷史）。RightShip 公開說明：Safety Score 由事故、DOC 公司績效、PSC 缺失、留置、船旗、船級六個子分數組成（事故與 DOC 公司績效影響最大，回溯 5 年）；2025-08-20 起 PSC 缺失分低／中／高嚴重度；GHG Rating 自 2023-12-06 改為 A–E。計分規則待取得 RightShip 平台資料或匯出格式後接入。
- 升級後請在 Apps Script 執行一次 `setup` 建立 `RightShip` 分頁。

## VIR 報告 PDF 自動匯入與缺失數比對（v1.8–v1.10）

- 在「訪船紀錄」或某筆訪船頁按 **上傳 VIR 報告 PDF**，選擇或拖曳 PDF（可一次多份）。PDF 在瀏覽器內讀取（pdf.js，由 cdnjs 載入），不經第三方服務。
- **讀取方式**：依文字座標重組表格欄位（編號、缺失說明 Remark、矯正要求 Action Required、期限、PMS／PSC／VIQ 代碼、評分），項目名稱（BNWAS、ECDIS…）取表格上方的標題。以報告最後的 **DEFECT SUMMARY** 為準逐項擷取。
- **三方比對**：① 封面「31 Defects (out of 770 Tasks)」與各類別數量；② DEFECT SUMMARY 擷取數；③ 各章節題目中評分 1–3 的項目（交叉檢查有無漏列）；④ 系統已登錄數。逐章節列出，不符時標紅；③ 有、② 沒列的項目另外提醒，不自動匯入。
- **對應訪船編號**：檔名開頭是訪船編號（例 `TEH-VICTORY-2026-01-MGR-VIR_VIR Report.pdf`）會自動對應；在某筆訪船頁上傳則歸到該筆；都沒有時依船名與年度產生新編號（可修改）。
- **匯入**：沒有的訪船紀錄自動建立；依編號（4.016…）去重，已有的項目不覆蓋原文字（例如中文整理過的說明），只補齊章節、項目、檢查題目、代碼與空白欄位，並寫入處理紀錄。同一份報告重複上傳不會重複建立。可選擇同時更新訪船資料（評分、缺失數、題數、章節分布、報告狀態、檢查人員、地點）與把 PDF 以 VIR 類別歸檔到 Drive。
- **訪船頁比對面板**：依「報告各章節缺失數」（`reported_breakdown`，格式 `Radio / Navigation=6; Technical=12`）逐章比對已登錄數；報告狀態是 In progress（未定稿）時提醒定稿後再上傳一次。訪船卡片顯示「與報告相符」或差幾項。
- **v1.8.1 修正**（以 TS-OSAKA-2026-04-MGR-VIR 驗證，報告 23 項）：
  - 沒有題號的列（Miscellaneous 的「Please add any other observations / missed items here」）以評分欄判斷為一列，列表顯示「無題號」，重複上傳時以缺失說明去重。
  - 封面「23 Defects」與第一個類別印在同一行時也讀得到摘要數字。
  - 跨頁的缺失說明會接上下一頁的內容。
  - 章節標題後的項目名稱印在上一頁底部時也讀得到。
  - PHOTO REPORT 之後的頁面不再讀入。
  - 頁尾沒有結尾逗號時也讀得到報告狀態。
- **支援格式**（自動判斷，同一次可混合上傳）：
  - **FML（Paris 系統）VIR**：以 DEFECT SUMMARY 為準，與封面摘要逐章節比對（見上）。
  - **V.Ships（Shipsure「INSPECTION SUMMARY」）**（v1.9）：每筆缺失讀出編號（例 M26/0023）、Insp. Ref.、類型（Deficiency／Observation，存在 `ftype` 欄並以標籤顯示）、System / Area（作為章節）、Details、期限與 Cleared 日期；Actions 表的回報人一併帶入。這種報告沒有封面缺失總數，改以四項檢查確認沒有漏讀：Insp. Ref. 1–N 連號、缺失編號不重複、已清除項目都有 Actions 紀錄、Actions 表的編號都找得到缺失。報告上已有 Cleared 日期的項目匯入後直接為「待確認」（提交日 = 清除日，矯正措施記「報告記錄已於 … 清除（回報人）」），由 PIC 確認關閉；之後上傳新版報告時，原本待改善的項目若已清除也會改為待確認。檢查意見（Comments）寫入訪船備註。
  - **BSM（Ship Inspection Report）**（v1.10）：以附錄「SUPERINTENDENT VESSEL INSPECTION」缺失單為準，每項讀出 Sl No（編號 TSI-01…）、檢查題目、缺失描述、嚴重度（Deficiency）、SubCategory（作為章節）、SOC Level 3（作為項目）、直接原因與根本原因（寫在缺失說明下方）、矯正措施與負責職位、期限。交叉檢查：附錄 Sl No 連號；附錄每一項都對回主文題目；該題在主文評為 No／Fair／Poor；主文所有評為 No／Fair／Poor 的題目都列入附錄（沒列的會提醒、不自動匯入）。主文題數與評語數一併顯示。
    - **沒有附錄缺失單的 BSM 報告**（v1.10.1，例 TS HongKong 2026-05）：有些報告只寫「另記為 NC／Observation」，清單不在 PDF。系統改從主文評語擷取：評為 No／Fair／Poor 的題目，加上評語 Yes 但留言註明 recorded as NC／observation／finding 的題目；編號 Q章節.題號（例 Q4.23），類型依留言分為 Deficiency／Non-conformity／Observation；Not Seen 不列為缺失。畫面會提醒向 BSM 索取正式清單核對。這類報告沒有期限，匯入時可設定「沒寫期限的項目」的改善期限（預設 30 天後，空白 = 不設）。
  - 其他格式讀不到時會提示改用「匯入缺失（貼上）」。
- **大檔自動壓縮**（v1.10）：船管報告多因照片超過 20 MB。上傳時（VIR 報告、文件歸檔、缺失佐證）超過 20 MB 的 PDF 會在瀏覽器內重新壓縮 PDF 裡的照片（依序長邊 1600／1280／1024／800 px，壓到 20 MB 以內為止），文字、表格與向量圖不變，仍可搜尋與複製；超過 20 MB 的照片檔縮小後上傳。歸檔說明會註記原檔大小。壓縮元件 pdf-lib 由 cdnjs 載入。實測 BSM Kota Valparaiso 報告 27.8 MB → 19.0 MB（長邊 1280 px，約 12 秒）；TS HongKong 66.5 MB → 15.1 MB（長邊 1600 px，約 20 秒）。報告的缺失擷取一律用原檔，不受壓縮影響。
- 升級後請在 Apps Script 執行一次 `setup`，新增欄位：Visits 的 `reported_breakdown`、`tasks`、`report_status`；VisitItems 的 `question`、`pms_code`、`psc_code`、`viq_code`、`score`、`ftype`。

## 訪船缺失管理（v1.7）

- 第三個主分類「訪船缺失」，放在事故管理、PSC 檢查旁邊，有四個分頁：總覽、訪船紀錄、缺失追蹤、船舶履歷。
- **訪船紀錄**：每次登輪一筆，編號沿用船管登輪審查系統的配號（船名-年度-序號-檢查方-類別，例 TEH-VICTORY-2026-01-MGR-VIR）。輸入編號會自動帶出船舶、檢查方（MGR 管理公司、OWN 船東…）與類別（VIR、VST、ISA…）；船東自行訪船沒有配號時可按「產生編號」。記錄登輪期間、地點、檢查人員、報告評分、報告缺失數與報告連結；報告缺失數和系統登錄數不同時會提醒補齊。
- **匯入缺失**：在訪船頁按「匯入缺失（貼上）」，可貼 Excel／VIR 匯出的表格（編號、項目、缺失說明、矯正要求、改善期限），或條列文字（Gemini 整理的「項目 4.016 (BNWAS)／缺失說明／矯正要求／改善期限」格式可直接貼），先預覽再匯入；重複項目自動略過。FML VIR 的編號會自動對應章節（4 = Radio/Navigation、5 = Safety / LSA / FFA、9 = Mooring、10 = Technical、11 = Deck…）。
- **追蹤流程**：待改善 →（船管提交矯正措施）待確認 →（PIC 確認）已關閉；不合格可退回並寫原因；admin 可撤銷登錄錯誤的項目。每一步寫入該項的處理紀錄與 AuditLog。超過改善期限仍待改善的列為逾期，每日 07:00 提醒信也會列出。
- **批次處理**：勾選多項，一次提交或關閉（同一份 CAR 回覆多項時用），已填過矯正措施的項目保留原內容。
- **文件**：報告（VIR）、矯正報告（RECT）、佐證（EVID）上傳到 Drive「訪船 / 年度 / 訪船編號」；在缺失視窗上傳的佐證會連到該項。
- **總覽**：待改善、逾期、待確認、14 天內到期、關閉率與準時率；各管理公司的訪船次數、缺失數、逾期、準時提交率與平均關閉天數（可作為監督船管的紀錄）。
- **船舶履歷**：每艘船把訪船（各檢查方）、PSC 檢查與事故依時間排在一起，可依來源篩選，並列出各方最常指出的項目。
- 升級後請在 Apps Script 執行一次 `setup`，建立 `Visits`、`VisitItems` 兩個分頁；再執行「TSL PSC → 套用欄位下拉選單與保護」。

## 週報／月報（v1.6）

## 船舶事故與趨勢（v1.5）

- **事故管理 → 船舶事故**：每艘船一張卡片，顯示事故件數（T1 / T2 / T3）、進行中件數、近 12 個月風險分數與近 4 年每年分數長條。點卡片進入該船「有紀錄以來」的事故時間軸（依年份分組，每年的分數與等級、每件事故的分級、狀態、摘要），點事故可開啟事故頁。
- **事故風險計分**（依每年事故嚴重性）：Tier 1 = 10、Tier 2 = 4、Tier 3 = 1，4.1 重大事件另加 5，PSC 檢查產生的事故 × 0.5，作廢不計；近 12 個月（或單一年度）≥ 15 高風險、≥ 8 偏高、≥ 3 一般。存在 Settings 的 `inc_risk_weights`、`inc_risk_levels`，也可在「事故規範 → 事故風險計分」修改。
- **PSC 高風險船紅框**：Tokyo MOU 績效 Low / Very Low 的船，在 PSC 船舶檔案與船舶事故卡片上加紅框，並有燈條沿邊框慢速繞行 10 秒後停在紅框（系統設定「減少動態效果」時只顯示紅框）。
- **缺失趨勢圖**：PSC 船舶檔案上方是船隊每季缺失比，點船進入後是該船每次檢查的缺失比；紅色虛線為 Tokyo MOU 平均缺失指數（Settings `tmou_avg_deficiency_index`）。拖曳下方時間軸或拉動兩側把手選期間，右側即時顯示平均、與基準的差、趨勢（每年斜率）、期間變化量與判讀（高於基準且上升 → 優先介入；低於基準但上升 → 提前預防）。
- **船隊事故嚴重性趨勢**：船舶事故頁上方，每季事故分數合計，虛線為全期每季平均，同樣可以拖曳時間軸。

## 回信範本（管理公司各階段通報後回覆）

- 事故頁按「回信範本」，系統依事故進度建議範本（標「建議」）：收到立即通報（立案與編號通知）→ 收到初步報告（狀態更新與督導）→ 收到進度更新 → 收到 RCA（審查意見）→ 結案通知；報告逾期時建議「逾期催報」。
- 自動帶入事故編號、船名、日期（12-Jul-2026 格式）、地點、分級與性質（英文）、管理公司、TSL PIC、P002 期限（初報、進度更新、RCA）、逾期項目、6.6.4 結案四項、矯正措施。
- 填「船長姓名」「事故英文名稱」後，主旨與內文即時更新；【】是要人工填寫的地方，視窗下方會提醒還有幾處沒填。內文可直接修改。
- 「複製內文」貼到 Outlook；「開啟郵件」會帶入收件人、副本與主旨（內文太長時先自動複製）。寄出後按「記錄已回覆」，事故頁會留下回信紀錄（UTC 時間、範本、回覆人），也寫入 AuditLog。

## 日常使用

- **各船回傳 PSC 報告**：PSC 檢查 → 檢查登錄 → 新增 PSC 檢查（或事故管理 → 事故登錄與處理 → 登錄 PSC 檢查）→ 填日期、船、港口與缺失 → 儲存。系統會配發事故編號，並同步寫入事故登錄器。
- **其他事故**：事故管理 → 事故登錄與處理 → 新增其他事故，取得編號後在事故頁上傳船方報告與 Template 1–5C，填矯正措施後結案。
- **上傳文件**：在案件頁選文件類別後上傳，系統自動改名並歸檔。文件類別包括 PSC Form A／B、船舶矯正報告、佐證、Template 1–5C。
- **矯正追蹤**：逐項勾選「已改正」、填改正日期與矯正措施。全部改正後按「結案」，事故登錄器同步改為「已完成」。
- **船舶改名或換管理公司**：系統管理 → 船隊資料。舊資料填上失效日，再新增一筆同 IMO、填生效日的資料。之後的事故編號會自動用新船名與新公司碼。
  - 例：TS SHENZHEN 至 2026/01/17，TEH PEACE 自 2026/01/18 起。

## 更新程式

**v1.10.2 起每次更新都要一起換這四個檔案**：`index.html`、`assets/core.js`、`assets/app.js`、`assets/app.css`。`index.html` 載入程式時帶版本號（例 `core.js?v=1.10.2`），瀏覽器才會抓新檔、不沿用快取。頁首「資料截至」旁會顯示目前執行的版本（例 v1.10.2）。如果 `app.js` 與 `core.js` 版本不同（漏換檔案或瀏覽器快取），頁面頂端會出現紅色警示；網頁與後端 Apps Script 版本不同時出現黃色提醒。


1. 修改 `assets/core.js` 後，同步複製到 `apps-script/core.gs`，貼回 Apps Script；`Code.gs` 有改也要一起貼回。
   - 新版本新增分頁或欄位時，先執行一次 `setup`，它只會補欄位，不會清除資料。
2. 在 Apps Script「部署 → 管理部署作業 → 編輯 → 新版本」。網址不變。
3. 前端推到 GitHub 後自動更新。
4. 執行 `npm test` 可跑核心規則與 Apps Script 模擬測試（需要 Node.js 18 以上）。

## 限制

- 單檔上傳上限 20 MB（Apps Script 單次請求約 50 MB，base64 編碼會增加約 33%）。
- 「資料截至」以最新一次檢查或事故日期為準。
- 從事故登錄器匯入的舊事故沒有通報文件紀錄，立即通報與初步報告顯示「未追蹤」。
- 歷史文件（SharePoint「04-2. Accident Report」）尚未搬入；新案件起由系統歸檔。
